# 软件项目团队案例（脱敏版）

这是一个虚构的软件项目团队案例，用来说明“一个 AI 总控如何管理多个角色”。

它保留的是协作结构，不保留任何真实团队路径、真实群、真实项目规则或真实角色细节。

---

## 项目背景

一个小团队要做“客户问题跟踪面板”。

老板的原话大概是：

> 我不想每天问谁处理到哪了。能不能有个页面，让我看到问题数量、处理状态、负责人和最近进展？

这类需求看起来很简单，但很容易做乱。

因为它同时涉及：

- 需求范围
- 页面字段
- 数据来源
- 开发实现
- 测试验收
- 文档说明
- 后续维护

如果一个 AI 会话从头干到尾，很容易变成：需求没收口、代码先动了、页面做出来了但没人知道怎么验收。

---

## 角色分工表

| 角色 | 负责什么 | 不负责什么 | 交付物 |
| --- | --- | --- | --- |
| 总控 | 拆任务、定边界、派单、回收验收 | 不亲自包办所有执行 | 子任务列表、验收结论 |
| 产品经理 | 定义本期范围和不做范围 | 不直接改代码 | 需求说明、验收标准 |
| 架构/技术负责人 | 判断技术方案和影响范围 | 不扩大业务需求 | 技术方案、风险说明 |
| 开发执行 | 按方案实现功能 | 不自行增加需求 | 变更说明、自测结果 |
| 测试验收 | 按验收标准检查 | 不替产品改范围 | 问题清单、复测结论 |
| 文档/复盘 | 记录当前状态和过程经验 | 不决定是否上线 | STATE/progress 更新建议 |

这个表的重点不是角色多，而是每个角色都知道“自己不负责什么”。

## 一轮真实感流程

### 1. 用户提出需求

用户说：

```markdown
我想做一个客户问题跟踪面板，能看到每个问题的状态、负责人和最近进展。先做一个能用的版本。
```

如果主代理马上开始写代码，就已经偏了。

team-boss 应先收口：

```markdown
本轮目标：做一个可验收的最小版本。
本轮不做：权限系统、自动提醒、复杂统计、外部平台接入。
需要先让产品经理写清楚字段和验收标准。
```

### 2. team-boss 拆解

team-boss 拆成五个子任务：

1. 产品经理：定义本期字段和验收标准。
2. 技术负责人：判断数据结构和页面影响范围。
3. 开发执行：按确认后的字段实现页面。
4. 测试验收：按验收标准检查。
5. 文档/复盘：把当前状态写回项目文件。

派单时必须写清楚禁止事项：

```markdown
禁止事项：
- 不做权限系统
- 不做自动通知
- 不改无关页面
- 不引入外部平台
- 不把建议直接写成已完成事实
```

### 3. 子代理执行

产品经理输出：

```markdown
本期包含：
- 问题标题
- 当前状态
- 负责人
- 最近进展
- 更新时间

本期不包含：
- 权限管理
- 自动提醒
- 多维统计
- 导出功能

验收标准：
- 页面能看到问题列表
- 能按状态筛选
- 每条问题能看到负责人和最近进展
- 空数据时有明确提示
```

技术负责人输出：

```markdown
建议先用现有项目结构增加一个简单列表页。
第一版字段保持静态或来自示例数据。
后续再对接真实数据来源。
风险：如果一开始接复杂数据源，会拖慢验证。
```

开发执行输出：

```markdown
已按字段实现列表页候选方案。
未做权限、自动提醒、导出。
自测：列表展示、状态筛选、空状态提示通过。
```

测试验收输出：

```markdown
通过项：列表展示、状态筛选、负责人字段、空状态。
问题项：更新时间格式需要统一。
建议：不阻塞本轮验收，但应写入下一轮优化。
```

### 4. 主代理验收

主代理不能只看“已完成”。

它要对照最初的边界：

- 是否做了本期包含内容？
- 是否偷偷做了本期不包含内容？
- 是否有证据说明自测通过？
- 是否有问题被隐藏？
- 是否需要更新项目当前状态？

验收结论示例：

```markdown
本轮可以进入人工预览。

通过原因：本期字段和筛选已覆盖，未扩大到权限和自动提醒。

保留问题：更新时间格式不统一，写入下一轮 progress，不阻塞当前版本。
```

### 5. STATE / progress 回写

STATE 只写当前稳定事实：

```markdown
当前阶段：testing
当前目标：人工预览客户问题跟踪面板第一版
当前事实：第一版只包含问题列表、状态筛选、负责人、最近进展
明确不做：权限系统、自动提醒、导出功能
```

progress 记录本轮过程：

```markdown
本轮完成：产品范围、技术方案、列表页候选、测试验收。
发现问题：更新时间格式不统一。
下一步：人工预览后决定是否进入第二轮优化。
```

## 错误做法 vs 正确做法

| 场景 | 错误做法 | 正确做法 |
| --- | --- | --- |
| 用户提需求 | 立刻让 AI 写代码 | 先让 PM 写本期包含和不包含 |
| 任务拆解 | 一个会话从头做到尾 | team-boss 拆成产品、技术、开发、测试、文档 |
| 子代理派单 | “你去做一下” | 明确目标、输入、禁止事项、输出格式 |
| 验收 | 子代理说完成就通过 | 主代理对照验收标准复核 |
| 项目状态 | 过程全堆在聊天里 | 当前事实写 STATE，过程写 progress |
| 范围控制 | 顺手加权限和通知 | 本轮只做最小可验收版本 |
| 团队经验 | 所有经验混在一起 | 角色经验归角色，团队边界归 registry |

## 读者怎么改成自己的团队

你可以按下面步骤改：

1. 把“客户问题跟踪面板”换成你的项目。
2. 保留六个角色，但可以先只启用三个：总控、产品经理、测试验收。
3. 把“本期不做”写得比“本期要做”更清楚。
4. 每个子任务都加上禁止事项。
5. 每轮结束后，只把稳定事实写入 STATE，把过程写入 progress。
6. 如果团队变多，再引入 team-registry，不要先写一堆角色档案。

最小可复制版本：

```markdown
用户需求：<一句话需求>
本轮目标：<只做一个最小版本>
本轮不做：<列出 3-5 个明确不做项>
角色：总控 / 产品经理 / 开发执行 / 测试验收
验收：每个结论必须对应本轮目标，不能扩大范围
回写：当前事实进 STATE，过程进 progress
```

这个案例真正想传达的是：

团队协作不是让更多 AI 一起热闹，而是让每个角色都被边界约束住。
