# 六个页面设计

一个最小 Dashboard 可以先做六页。

它的目的不是好看，而是缓解六种焦虑：服务是不是在跑、角色是不是清楚、任务是不是执行、技能是不是可用、流程是不是卡住、用量是不是异常。

如果暂时不做后端，也可以先用 Markdown 表格或电子表格模拟。先把字段说清楚，再考虑页面和接口。

---

## 1. 端口状态

解决的焦虑：服务到底有没有起来？

第一版字段：

| 字段 | 说明 |
| --- | --- |
| 服务名 | 例如 dashboard-frontend、api-server |
| 端口 | 服务监听端口 |
| 状态 | online / offline / unknown |
| 最近检查时间 | 人工或脚本检查时间 |
| 证据 | 命令结果摘要或检查来源 |
| 备注 | 异常说明 |

不做后端时，可以先这样写：

```markdown
| 服务名 | 端口 | 状态 | 最近检查时间 | 备注 |
| --- | --- | --- | --- | --- |
| demo-frontend | 3000 | unknown | 待检查 | 第一版只记录预期端口 |
```

不要一开始做自动启停。先把“状态能不能说清楚”做好。

---

## 2. Agent / 角色

解决的焦虑：系统里到底有哪些角色？谁负责什么？

第一版字段：

| 字段 | 说明 |
| --- | --- |
| team_id | 团队标识 |
| role_id | 角色标识 |
| 职责 | 一句话说明 |
| 禁区 | 这个角色不能做什么 |
| 记忆状态 | none / basic / active |
| 最近更新 | 角色档案最近修改时间 |

Markdown 模拟版：

```markdown
| 团队 | 角色 | 职责 | 禁区 | 记忆状态 |
| --- | --- | --- | --- | --- |
| product-team | product-manager | 定范围和验收 | 不改代码 | basic |
```

不要把角色写成小说人物。角色越玄，越难验收。

---

## 3. 定时任务

解决的焦虑：自动任务是不是按计划执行了？

第一版字段：

| 字段 | 说明 |
| --- | --- |
| 任务名 | 任务标识 |
| 计划 | 执行频率或时间 |
| 上次结果 | success / failed / unknown |
| 下次时间 | 预计下一次执行 |
| 产物 | 结果文件或摘要 |
| 异常 | 如果失败，写一句原因 |

不做后端时，先人工维护最近三条任务即可。

不要一开始做复杂调度器。先能看见“有没有执行、结果是什么”。

---

## 4. 技能

解决的焦虑：AI 到底有哪些可复用能力？哪些已经过期？

第一版字段：

| 字段 | 说明 |
| --- | --- |
| 技能名 | 可复用流程名称 |
| 适用场景 | 什么时候用 |
| 禁止场景 | 什么时候不要用 |
| 最近验证 | 最近一次确认可用的时间 |
| 风险 | 容易踩坑的地方 |

Markdown 模拟版：

```markdown
| 技能 | 适用场景 | 禁止场景 | 最近验证 | 风险 |
| --- | --- | --- | --- | --- |
| article-review | 发布前审稿 | 不负责真实发布 | 待验证 | 容易扩大到改写全文 |
```

技能页不是技能全文仓库，只做入口和状态。

---

## 5. 流水线

解决的焦虑：一个任务现在卡在哪一步？

第一版字段：

| 字段 | 说明 |
| --- | --- |
| 流程名 | 例如文章终审、资料包复审 |
| 当前阶段 | planning / drafting / review / ready |
| 最近产物 | 文件路径或产物名称 |
| 阻塞点 | 等待谁确认，或缺什么输入 |
| 下一步 | 明确一个动作 |

不做后端时，可以给每条流水线一张 Markdown 卡片。

```markdown
## 资料包 v1.1
当前阶段：review
最近产物：packages/hermes-genesis-season1-practical-pack/
阻塞点：等待人工复审
下一步：根据复审意见做小修
```

不要一开始做复杂甘特图。先把“卡在哪里”写清楚。

---

## 6. 用量观察

解决的焦虑：模型调用有没有异常？成本有没有失控？

第一版字段：

| 字段 | 说明 |
| --- | --- |
| 日期 | 统计日期 |
| 模型 | 使用的模型名称 |
| 调用次数 | 当天大概次数 |
| 任务类型 | 写作 / 审计 / 开发 / 检查 |
| 异常说明 | 是否有异常峰值 |

如果没有自动统计，第一版可以只写人工估算和异常备注。

不要为了精确统计，先引入复杂系统。用量页第一目标是发现异常，不是做财务报表。

---

## 不做后端时的最小模拟法

你可以先建一个 `dashboard.md`：

```markdown
# Demo Dashboard

## 服务状态
表格...

## 角色状态
表格...

## 任务状态
表格...

## 技能状态
表格...

## 流水线状态
卡片...

## 用量观察
表格...
```

每周人工更新一次。

如果这份 Markdown 都维护不住，说明真实 Dashboard 还太早。

---

## 第一版不要做什么

- 不做自动控制台。
- 不做复杂权限系统。
- 不做实时推送。
- 不做漂亮但无来源的数据大屏。
- 不做完整后端打包。
- 不把 Dashboard 当成事实源。

Dashboard 是展示层。

它可以帮你看见系统，但不能替你定义事实。
