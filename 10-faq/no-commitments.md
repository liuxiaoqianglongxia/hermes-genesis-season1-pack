# 不承诺事项

为了避免误解，这里把边界再写清楚。

这份资料包不承诺：

- 不承诺是完整 Hermes。
- 不承诺是商业系统。
- 不承诺一键安装。
- 不承诺适配所有电脑环境。
- 不承诺包含完整 Dashboard 后端。
- 不承诺替你接入自己的平台。
- 不承诺一对一部署服务。
- 不承诺远程排错直到跑通。

这份资料包承诺的是：

- 尽量把第一季的可复用结构讲清楚。
- 尽量给出可以照着改的模板。
- 尽量把常见翻车点提前写出来。
- 尽量让你知道哪些东西先做，哪些东西别一上来就抄。

---

## 为什么不提供完整 Hermes

因为完整系统里会包含大量个人环境、团队边界、历史决策和运行习惯。

这些东西直接给出去，不但对别人未必有用，还容易造成误导。

真正可复用的是：

- 目录怎么分层
- 事实源怎么确定
- team-boss 怎么派单
- 子代理怎么限边界
- 角色经验怎么沉淀
- Dashboard 怎么看见系统

所以资料包提供的是脱敏后的结构和模板，不是完整内部系统。

---

## 为什么不提供一键安装器

一键安装器听起来省事，但现在不是最好的选择。

原因很简单：每个人的电脑、模型、项目目录、使用平台都不一样。

过早做安装器，很容易变成：

- A 的电脑能跑，B 的电脑跑不了。
- 用户以为安装完就是完整系统。
- 大量时间耗在环境适配，而不是理解方法。
- 最后变成一对一排错。

第一季资料包更适合先让你看懂“从哪里开始搭”。

理解了结构，再决定要不要自动化。

---

## 为什么 Dashboard 后端不打包

Dashboard 后端最依赖本地数据来源。

比如：

- 服务状态从哪里来
- 任务结果从哪里来
- 角色信息从哪里来
- 项目进度从哪里来
- 用量统计从哪里来

这些来源每个人都不同。

如果直接打包一个后端，很可能会出现页面能打开、数据却不真实的问题。

所以资料包只给：

- 六页结构
- 字段设计
- 可观测思路
- Markdown / 表格模拟方法
- 哪些东西不要一上来复制

等你自己的事实源稳定了，再接后端才有意义。

---

## 为什么真实 team-registry 和团队技能不能原样给

真实团队配置里往往包含：

- 真实团队边界
- 真实项目习惯
- 内部协作规则
- 历史经验
- 特定业务语境

这些内容原样给出去，会有两个问题：

1. 不适合你的团队，容易照抄后更乱。
2. 不适合公开交付，容易混入不该公开的信息。

资料包给的是脱敏版本：

- 用通用 product-team / engineering-team / content-team 举例。
- 用 demo 项目代替真实项目。
- 保留结构，不保留私有细节。

你应该复制的是“边界设计方法”，不是别人的团队档案。

---

## 如果想继续深入，下一步怎么学

建议顺序：

1. 先用 demo 项目跑通 README、STATE、progress、registry 分工。
2. 再给自己的项目补 STATE 和 progress。
3. 然后引入 team-boss，让它只做派单和验收。
4. 再加 2-3 个角色，不要一开始写很多角色。
5. 每次任务结束后，只沉淀对未来有用的经验。
6. 最后用 Markdown 表格模拟 Dashboard。
7. 当你能稳定维护表格，再考虑做页面和后端。

如果你的目标是研究和改造，它会有帮助。

如果你的目标是下载后直接拥有完整系统，它不适合。
