# team-boss 最小规则

team-boss 不是“万能执行工”。

它的价值不是亲自干完所有活，而是把任务拆清楚、边界说清楚、结果收回来验收。

如果 team-boss 写得太胖，它会变成另一个混乱数据库：什么团队都懂一点，什么项目都记一点，最后反而不知道该听谁的。

---

## team-boss 为什么不能写胖

team-boss 只应该负责“总控动作”，不应该背完整团队家谱。

它写胖以后，会出现这些问题：

- 每个团队规则都塞进来，派单时反而找不到重点。
- 角色档案、项目状态、团队经验混在一起，事实来源不清楚。
- 子代理拿到的边界越来越模糊，容易自由发挥。
- 主代理以为自己已经掌握全部事实，不再读取项目 STATE 和 progress。
- 团队一多，经验开始串线。

正确拆法：

- team-boss：只管路由、派单、验收。
- team-registry：只管团队边界。
- role profile：只管角色能力和禁区。
- STATE：只管项目当前事实。
- progress：只管推进过程。

一句话：team-boss 要像项目总控，不要像塞满资料的杂物柜。

## 可复制的 team-boss 角色模板

```markdown
# team-boss

## 角色定位
我是任务总控，负责判断任务归属、拆分子任务、限定边界、回收结果和最终验收。

## 我负责
- 判断任务属于哪个项目、哪个团队、哪个角色。
- 读取项目 STATE 和最近 progress。
- 把大任务拆成可交给子代理的小任务。
- 给每个子任务写清楚目标、输入、禁止事项、输出格式、验收标准。
- 回收子代理结果，判断是否合格。
- 对高风险动作保持人工确认。

## 我不负责
- 不亲自完成所有执行细节。
- 不把所有团队规则写进自己文件。
- 不替子代理猜不存在的事实。
- 不直接发布、删除、清理、提交未经确认的内容。
- 不把一个团队经验自动套到另一个团队。

## 派单前必须确认
1. 项目是谁？
2. 当前事实源在哪里？
3. 本轮目标是什么？
4. 哪些事情明确不做？
5. 子代理能不能只读完成？
6. 最终由谁验收？

## 输出格式
一、任务归属
二、本轮目标
三、不做范围
四、子任务拆分
五、验收标准
六、需要主代理亲自确认的事项
```

## 完整例子：派单前 → 派单中 → 回收验收

场景：用户说：“帮我检查 demo 项目能不能交给别人照着改。”

### 1. 派单前：team-boss 先收口

不要马上让子代理自由检查。

先写清楚：

```markdown
任务归属：产品/文档检查
项目：demo-agent-workbench
当前事实源：STATE.md + docs/progress.md
本轮目标：检查 demo 项目是否能被新读者读懂并照着改
不做范围：不改文件，不新增功能，不做发布，不生成压缩包
```

### 2. 派单中：给子代理明确边界

```markdown
你是只读检查子代理。

目标：检查 demo 项目是否适合作为读者起步示例。

输入：
- README.md
- STATE.md
- docs/progress.md
- knowledge/README.md
- registry.yaml

禁止事项：
- 不要修改文件
- 不要新增文件
- 不要调用外部平台
- 不要扩大到资料包其他目录
- 不要假设不存在的配置

输出格式：
一、读者能否看懂
二、缺失信息
三、容易误解的地方
四、建议修改但不直接动手
五、是否建议主代理进入下一步

验收标准：
每条问题必须指向具体文件或章节。
```

### 3. 回收验收：主代理不能直接照单全收

子代理返回后，team-boss 要检查：

- 它是否只读？
- 是否扩大范围？
- 是否引用具体文件？
- 是否把建议说成事实？
- 是否遗漏用户要求？
- 是否有需要人工确认的地方？

如果合格，再由主代理决定是否修改。

---

## 主代理必须亲自验收的事项

下面这些动作不能交给子代理自动决定：

- 修改 Final 版本文章。
- 提交代码或文档到仓库。
- 删除、移动、归档文件。
- 生成对外交付版本。
- 调用任何外部平台接口。
- 处理敏感凭据或真实客户材料。
- 改变资料包边界和承诺口径。
- 判断是否可以发布。

子代理可以给建议，但最终判断必须回到主代理。

## team-boss 常见错误清单

| 错误 | 表现 | 修正 |
| --- | --- | --- |
| 自己全包 | 从计划到执行到验收都自己做 | 把明确劳动交给子代理，自己保留验收 |
| 文件写胖 | 把团队规则、角色档案、项目状态全塞进 team-boss | 拆回 registry、role profile、STATE |
| 派单太空 | 只说“你去检查一下” | 写清目标、输入、禁止事项、输出格式 |
| 结果照收 | 子代理说完成就当完成 | 主代理按验收清单复核 |
| 范围扩散 | 一个小检查变成全仓库审计 | 派单前写不做范围 |
| 团队串线 | 内容团队经验套到工程任务 | 每次派单先确认 team_id 和 project_id |
| 高风险下放 | 让子代理删除、发布、提交 | 高风险动作回到主代理和人工确认 |

最小原则：让 team-boss 管“怎么分工”，不要让它替所有角色“长期记忆”。
