# demo 产品经理角色记忆

这个文件展示角色记忆怎么写。内容来自虚构 demo 项目，不是真实团队记忆。

## 经验记录：先写不做范围

### 适用场景

用户提出一个看似简单、实际可能扩大的需求。

### 有效做法

先把本期不做的内容写出来，再拆任务。

示例：

```text
本期只做：把项目首页的状态卡片改清楚。
本期不做：不重构后端、不新增权限系统、不改导航结构、不接入真实发布链路。
```

### 为什么有效

它能防止任务被越拆越大，也能让开发和测试知道边界在哪里。

## 经验记录：验收标准必须可检查

### 适用场景

任务要分给开发或测试角色。

### 有效做法

不要写“页面更好看”。

改成：

```text
验收标准：
1. 首页显示 4 张状态卡片。
2. 每张卡片都有名称、状态、来源、最近更新时间。
3. 如果来源缺失，页面必须显示“待接入”，不能显示假数据。
```

## 失败记录：只听子任务总结导致误判

### 发生了什么

开发角色说“已完成”，但没有给截图、文件路径、检查命令或对照结果。

产品经理直接把结果转给主代理，导致主代理以为任务完成。

### 后果

下一步进入验收时，才发现页面仍然显示旧内容。

### 以后怎么避免

子任务回收时必须带证据：

- 改了哪个文件。
- 解决了哪个问题。
- 如何验证。
- 还剩什么风险。

没有证据，只能算“待验收”，不能算“已完成”。

## 失败记录：没有读 STATE 就开始拆任务

### 发生了什么

产品经理只看了用户输入，没有读项目当前状态。

### 后果

拆出来的任务和项目当前阶段不一致，开发角色开始做已经废弃的功能。

### 以后怎么避免

每轮拆任务前先读：

1. README：知道入口在哪里。
2. STATE：知道当前事实。
3. progress：知道最近做到了哪一步。
4. registry：知道项目清单和边界。
